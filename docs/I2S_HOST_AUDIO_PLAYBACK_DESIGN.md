# RT685 I2S Host Audio Playback Design and Implementation Plan

**Target:** local `mimxrt685-evk` QEMU machine  
**Firmware:** `firmware/build/i2s_interrupt_record_playback.elf`  
**Host output:** QEMU audio backend, initially CoreAudio, Linux native audio,
and WAV  
**Guest format:** 48 kHz, stereo, signed 16-bit PCM  
**Accuracy target:** deterministic functional audio, not analog or cycle-accurate codec emulation  
**Status:** ready for implementation  
**Date:** 2026-10-26

> **Repository policy:** `qemu/AGENTS.md` and
> `qemu/docs/devel/code-provenance.rst` prohibit contributing AI-generated or
> AI-derived content to upstream QEMU. This work is for the local
> hardware-enablement project and must not be submitted upstream.

## 1. Outcome

Extend the current RT685 audio emulation so playback samples sent by the guest
through Flexcomm3 I2S can be heard through a host audio backend. Preserve the
existing paced I2S model and add a buffered boundary between the emulated
WM8904 DAC input and QEMU's callback-driven audio subsystem.

The first increment will provide:

- 48 kHz, stereo, signed 16-bit host PCM output;
- a bounded ring buffer between the I2S frame timer and host callback;
- CoreAudio output for interactive use on macOS;
- PipeWire, PulseAudio, or ALSA output for interactive use on Linux;
- WAV output for deterministic automated testing;
- an audible deterministic capture tone so the record/playback example has
  meaningful content without requiring a host microphone;
- clean start, stop, reset, shutdown, and migration behavior; and
- qtests plus a bounded firmware/WAV acceptance test.

Host microphone capture is a follow-up. The current SDK example records and
then plays back the same buffer, so a synthetic tone is needed initially: its
existing increment-by-one ramp is primarily sub-audible and would otherwise
sound like silence interrupted by periodic discontinuities.

## 2. Existing architecture

The current data path is:

```text
deterministic WM8904 capture ramp
             |
             v
WM8904 ADC endpoint --> Flexcomm1 I2S RX --> guest 400-byte buffer
                                                   |
                                                   v
WM8904 playback sink <-- Flexcomm3 I2S TX <---------+
        |
        +-- records last word/frame count, then discards the sample
```

`rt685-audio-link` owns the only 48 kHz virtual-time timer. Each tick moves one
32-bit stereo word in each direction. Flexcomm1 and Flexcomm3 own their FIFO
state and interrupts. The WM8904 owns control registers and the deterministic
capture source, but it currently has no QEMU audio voice.

The host-audio increment changes only the codec boundary:

```text
WM8904 playback endpoint
        |
        | one packed stereo word per I2S frame
        v
signed-16 conversion --> PCM ring buffer --> QEMU SWVoiceOut --> host backend
                                                  |               |
                                                  |               +-- CoreAudio
                                                  +------------------ WAV
```

The I2S link remains timer-driven. The host backend must not become the owner
of guest FIFO timing or directly invoke guest IRQ behavior.

## 3. Scope

### In scope

- QEMU output voice creation through `AudioBackend`/`SWVoiceOut`.
- An `audiodev` property on the WM8904 model.
- 48 kHz, two-channel, `AUDIO_FORMAT_S16`, little-endian output.
- Explicit extraction of left and right 16-bit samples from each I2S word.
- A fixed-size PCM ring buffer with partial-write support.
- Host callback draining, silence on underrun, and deterministic overflow
  handling.
- An audible deterministic tone generated by the WM8904 capture endpoint.
- Output enable/disable tied to the emulated stream lifecycle.
- WAV-based sample-format, channel-order, frequency, and duration tests.
- CoreAudio smoke testing on macOS.
- Reset and migration rules for backend-independent emulated state.

### Deferred

- Host microphone input and macOS microphone-permission handling.
- Dynamic host format changes based on every WM8904 clock/FLL register.
- Analog gain, mixer, mute ramp, filtering, clipping, and headphone impedance.
- Resampling guest formats other than 48 kHz stereo signed 16-bit PCM.
- Multiple output voices or physical jack routing.
- Lip synchronization or synchronization with unrelated emulated media.

Unsupported guest formats must not be silently interpreted as supported PCM.
They should leave the voice inactive and log a rate-limited guest error or
unimplemented message.

## 4. Source authority

Use the following checked-in sources and APIs:

1. `qemu/include/qemu/audio.h` for `AudioBackend`, `SWVoiceOut`,
   `audio_be_check()`, `audio_be_open_out()`, `audio_be_write()`, and voice
   activation.
2. `qemu/hw/audio/lm4549.c` and `qemu/hw/audio/pcspk.c` as lifecycle and
   callback examples.
3. `qemu/hw/audio/wm8904.c` and
   `qemu/include/hw/audio/wm8904.h` for the codec endpoint.
4. `qemu/hw/audio/rt685_audio_link.c` for frame cadence and routing.
5. `qemu/hw/char/rt6xx_flexcomm.c` for FIFO word packing and stream activity.
6. The pinned SDK example and `fsl_i2s.c` for the guest's actual format and
   transfer behavior.

The locally built macOS QEMU currently reports `coreaudio`, `sdl`, `wav`,
`dbus`, and `none` audio drivers. A Linux build will commonly provide
`pipewire`, `pa`, `alsa`, and/or `sdl`, depending on its configure-time
dependencies. WAV is the portable automated-test backend. Always check the
specific binary with `qemu-system-arm -audiodev help` before selecting a
backend.

## 5. Detailed design

### 5.1 Ownership

The WM8904 model owns host-facing audio because it represents the DAC sink.
Add these fields to `WM8904State`:

```c
AudioBackend *audio_be;
SWVoiceOut *voice;
int16_t playback_ring[PLAYBACK_FRAMES * 2];
uint32_t playback_read;
uint32_t playback_count;
uint64_t playback_dropped;
uint64_t playback_underruns;
bool voice_active;
```

Use a frame count rather than a byte count for ring indices. One frame is
always two adjacent `int16_t` samples: left, then right.

The audio-link object must remain independent of QEMU host audio APIs. This
keeps the board wire model deterministic and prevents host callback timing from
changing MMIO or interrupt ordering.

### 5.2 Audio backend and QOM property

Add `DEFINE_AUDIO_PROPERTIES(WM8904State, audio_be)` to the WM8904 property
table. During codec realization:

1. call `audio_be_check(&wm->audio_be, errp)`;
2. configure `audsettings` for 48000 Hz, two channels,
   `AUDIO_FORMAT_S16`, little-endian;
3. open `wm8904.out` with `audio_be_open_out()`; and
4. leave the voice inactive until playback data becomes available.

If no explicit property is assigned, `audio_be_check()` resolves QEMU's
default backend. This permits the board-internal codec to use the sole backend
created by:

```sh
-audiodev coreaudio,id=rt685
```

Backend initialization failure must fail device realization with a useful
error. The `none` backend remains valid for headless tests.

### 5.3 PCM word conversion

The existing endpoint contract carries one 32-bit word for one stereo frame.
For the supported SDK configuration:

```text
bits 15:0   left signed 16-bit sample
bits 31:16  right signed 16-bit sample
```

Convert explicitly instead of relying on host endianness:

```c
int16_t left = (int16_t)(word & 0xffff);
int16_t right = (int16_t)(word >> 16);
```

Store `left` followed by `right` in the ring. QEMU's voice is declared
little-endian, so its audio layer performs any backend conversion required by
the host.

Add a WAV test with distinct left/right values to prevent an unnoticed channel
swap or byte-order regression.

### 5.4 Ring buffer and backpressure

Use a power-of-two capacity of 4096 stereo frames, approximately 85 ms at
48 kHz. This is large enough to absorb normal callback granularity without
introducing excessive latency.

Producer behavior in `wm8904_endpoint_push()`:

1. decode the packed I2S word;
2. if space exists, append one stereo frame;
3. if full, drop the oldest frame, increment `playback_dropped`, and append the
   newest frame; and
4. activate the output voice if it is inactive.

Dropping the oldest frame bounds latency and lets audible playback recover
after host stalls. It must not stall the 48 kHz board timer or hold a guest
FIFO full.

Consumer behavior in the QEMU audio callback:

1. drain up to the backend's requested byte count;
2. handle ring wrap using at most two `audio_be_write()` calls;
3. honor partial writes and advance indices only for accepted complete frames;
4. if the ring becomes empty, leave it empty rather than inventing guest data;
   the QEMU backend supplies silence for unwritten space; and
5. increment `playback_underruns` once per transition from nonempty to empty
   while the guest stream remains active.

Never call blocking host APIs from the I2S endpoint push function.

### 5.5 Voice activation and stream state

The voice should be active while the guest TX endpoint is active or buffered
samples remain. Add a codec method or audio-link notification that supplies
the playback-stream state without making the codec inspect Flexcomm internals.

Required transitions are:

| Event | Voice/ring behavior |
|---|---|
| First playback frame | Activate voice and request a drain |
| TX temporarily underruns with `TXEMPTYZERO` | Queue the modeled zero frame |
| TX disabled or clock gated | Stop accepting new frames; drain queued frames, then deactivate |
| Peripheral reset | Flush ring and deactivate immediately |
| System shutdown/unrealize | Deactivate and close voice |

For the first implementation, activation on first frame and deactivation on
reset is sufficient if the voice remains active through temporary guest FIFO
underruns. A later refinement may add explicit stream-state notification.

### 5.6 Audible deterministic capture source

Replace the sub-audible ramp with a deterministic sine wave so the stock
record/playback example produces obvious output. Use:

- 440 Hz frequency;
- 48 kHz sample rate;
- stereo identical channels;
- amplitude no greater than 25% of signed 16-bit full scale; and
- a phase accumulator reset to zero on device reset.

Avoid runtime floating point. Use either a checked-in, locally generated lookup
table or a fixed-point phase accumulator and integer lookup. The phase state is
guest-visible through captured PCM and must therefore migrate.

Retain a QOM property selecting `ramp`, `tone`, or `silence`, with `tone` as the
EVK default. Tests may select `ramp` when exact successive values are more
convenient.

### 5.7 Timing

Continue producing exactly one frame per `rt685-audio-link` virtual timer tick.
Do not pace the guest directly from the host callback.

Improve the timer's fractional period handling as part of this work. Integer
division currently represents 48 kHz as 20,833 ns per frame, which introduces
long-term drift. Store a remainder accumulator so 20,833 ns and 20,834 ns
intervals average exactly 1/48,000 second.

Normal QEMU virtual time is close enough to wall time for interactive playback.
Modes that deliberately run virtual time faster or slower than real time may
overflow or underrun the host ring; the counters make this observable. Audio
must remain functionally safe in those modes even when it cannot sound normal.

### 5.8 Volume and mute

The first increment may output samples at the digital amplitude received from
the I2S link. Set the QEMU voice volume to full scale and limit the generated
tone amplitude for hearing safety.

Do not claim that WM8904 register-programmed analog volume is modeled. A later
increment can translate the relevant DAC/headphone mute and gain registers to
`audio_be_set_volume_out_lr()`.

### 5.9 Reset, migration, and shutdown

Reset must:

- clear ring indices and samples;
- deactivate the voice;
- reset tone phase;
- clear last-word and frame diagnostics; and
- clear drop/underrun counters.

Do not migrate `AudioBackend *` or `SWVoiceOut *`. They are host resources.
Migrate deterministic emulated state: ring contents and indices, tone phase,
and diagnostic counters. In `post_load`, reopen/reuse the destination voice,
validate ring indices, and reactivate it only if migrated buffered data exists.

If reliable cross-backend ring migration proves unnecessarily complex, the
acceptable alternative is to migrate tone phase and counters, flush the ring
on load, and document/test the resulting short audio discontinuity. Guest I2S
FIFO migration remains unchanged.

The device's unrealize/finalize path must deactivate and close the voice before
freeing state.

### 5.10 Diagnostics

Preserve the existing read-only `playback-frames` and `last-playback-word` QOM
properties. Add:

- `playback-buffered-frames`;
- `playback-dropped-frames`; and
- `playback-underruns`.

Do not log every underrun or dropped frame. Counters provide observability
without flooding `guest_errors` during startup or debugger pauses.

## 7. Test plan

### 7.1 Unit and qtests

Add tests for:

1. packed I2S word to left/right signed-16 conversion;
2. ring fill, wrap, partial drain, and FIFO ordering;
3. drop-oldest overflow behavior and counter increments;
4. empty-ring behavior and underrun accounting;
5. voice activation on first sample and deactivation on reset;
6. deterministic tone phase and reset reproducibility;
7. audio-link fractional cadence over at least 48,000 frames;
8. clock gating and reset stopping further playback production; and
9. migration with a partially filled ring or the documented flush-on-load
   behavior.

Tests should exercise guest MMIO and virtual time for integration behavior.
Private helper tests are appropriate only for isolated ring arithmetic.

### 7.2 WAV backend acceptance

Run the stock firmware with the WAV backend for a bounded interval. The exact
option spelling should be confirmed against the built QEMU version, using an
explicit backend ID. For the current tree, the intended command is:

```sh
qemu/build/qemu-system-arm \
  -M mimxrt685-evk \
  -kernel firmware/build/i2s_interrupt_record_playback.elf \
  -nographic \
  -audiodev wav,id=rt685,path=/tmp/rt685-audio.wav,\
out.frequency=48000,out.channels=2,out.format=s16
```

Validate the resulting file for:

- PCM encoding accepted by a standard WAV reader;
- 48,000 Hz sample rate;
- two channels;
- signed 16-bit samples;
- non-silent content;
- matching left/right channels for the initial mono tone;
- dominant frequency within a small tolerance of 440 Hz;
- no unexpected long zero gaps after startup; and
- duration consistent with the bounded virtual run.

The validator must use only the standard library if practical and must report
actionable failures rather than merely printing statistics.

### 7.3 CoreAudio smoke test

On macOS, launch with:

```sh
qemu/build/qemu-system-arm \
  -M mimxrt685-evk \
  -kernel firmware/build/i2s_interrupt_record_playback.elf \
  -nographic \
  -audiodev coreaudio,id=rt685
```

Expected behavior:

- firmware prints `Configure codec`, `Configure I2S`, and
  `Setup digital loopback`;
- a quiet 440 Hz tone becomes audible after the first guest buffer cycle;
- QEMU remains responsive to `Ctrl-A X`;
- no audio initialization errors appear; and
- `-d unimp,guest_errors` remains clean.

Do not automate subjective loudness. The WAV test is the reproducible
acceptance test; CoreAudio confirms integration with the actual host device.

### 7.4 Linux host smoke test

Use the first suitable backend listed by `-audiodev help`. PipeWire is the
preferred native backend on a modern PipeWire desktop:

```sh
qemu/build/qemu-system-arm \
  -M mimxrt685-evk \
  -kernel firmware/build/i2s_interrupt_record_playback.elf \
  -nographic \
  -audiodev pipewire,id=rt685
```

Fallbacks, when compiled into that QEMU binary, are:

```sh
-audiodev pa,id=rt685
-audiodev alsa,id=rt685
-audiodev sdl,id=rt685
```

Only one backend should be supplied for this board. Backend selection must not
change the WM8904 model or PCM format. Distribution packages may require an
additional QEMU audio package or plugin for the selected driver.

### 7.5 Regression tests

Run at minimum:

```sh
cmake -S firmware -B firmware/build -G Ninja \
  -DCMAKE_TOOLCHAIN_FILE=firmware/toolchain-gnu-arm.cmake
ninja -C firmware/build

ninja -C qemu/build qemu-system-arm tests/qtest/mimxrt685-test
QTEST_QEMU_BINARY="$PWD/qemu/build/qemu-system-arm" \
  qemu/build/tests/qtest/mimxrt685-test
```

Also verify the firmware under `-audiodev none,id=none` so headless execution
does not depend on a host sound device.

## 8. Implementation sequence

### Stage 1: PCM sink and WAV proof

1. Add the backend/voice property and lifecycle to WM8904.
2. Add the PCM ring and playback endpoint producer.
3. Implement the audio callback and partial drains.
4. Run through the WAV backend with directly injected known sample words.

**Exit criterion:** a WAV file contains correctly ordered 48 kHz stereo PCM
matching injected words.

### Stage 2: Audible capture tone

1. Add fixed-point tone generation and mode selection.
2. Reset and migrate tone phase.
3. Run the stock record/playback firmware into WAV.
4. Validate frequency, amplitude, channel order, and continuity.

**Exit criterion:** the unmodified example produces a deterministic 440 Hz WAV
through its RX-buffer-to-TX path.

### Stage 3: Lifecycle and timing hardening

1. Add fractional frame-period accumulation.
2. Test ring overflow/underrun policies.
3. Add reset, clock-gate, shutdown, and migration coverage.
4. Add QOM diagnostic properties.

**Exit criterion:** long bounded runs remain synchronized, observable, and
free of host-resource leaks or guest FIFO lockup.

### Stage 4: Host-backend acceptance

1. Run the firmware with the CoreAudio backend.
2. Run it with an available Linux native backend when a Linux host is
   available.
3. Confirm audible output and clean shutdown.
4. Run the existing RT685 qtest and firmware regression matrix.
5. Update the parent I2S design with final commands and measured results.

**Exit criterion:** audible playback works with the documented macOS command,
the backend-neutral WAV test passes, and a Linux command is documented and
validated when a Linux test host is available.

## 9. Acceptance criteria

The increment is complete when all of the following are true:

- Guest Flexcomm3 samples reach a QEMU host output voice in order.
- Output is 48 kHz stereo signed 16-bit PCM with verified channel order.
- The stock I2S record/playback firmware produces an audible deterministic
  tone without firmware source modification.
- WAV validation confirms the expected tone and contains no malformed or
  unexpectedly silent output.
- CoreAudio playback works using the documented command.
- Playback is backend-neutral; a supported Linux backend works without device
  model changes.
- Host backpressure never blocks the I2S timer or guest MMIO path.
- Overflow and underrun behavior is bounded, counted, and tested.
- Reset and clock gating stop new audio and leave no asserted guest IRQ caused
  by the host backend.
- Migration follows the documented preserve-or-flush policy and is tested.
- Headless `none` backend operation remains functional.
- Existing USART, I2C, SPI, I2S, and firmware tests do not regress.
- A bounded run remains clean under `-d unimp,guest_errors`.

## 10. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Host callback timing changes guest IRQ timing | Keep the audio-link timer as sole owner of I2S cadence; use a ring at the host boundary. |
| Writing one frame at a time causes noise or high overhead | Batch in the ring and drain contiguous spans from the callback. |
| Backend stalls create unbounded latency | Use a fixed-size ring and drop the oldest frame on overflow. |
| Virtual time runs faster than wall time | Keep bounded overflow behavior and expose counters; do not block emulation. |
| Channel order or endianness is wrong | Convert explicitly and validate distinct left/right WAV samples. |
| Existing ramp sounds like silence | Default the codec capture source to a low-amplitude 440 Hz tone. |
| Tone is unexpectedly loud | Limit generated amplitude to 25% full scale and document host volume responsibility. |
| Audio resources survive reset or shutdown | Centralize voice activation/close logic and test clean `Ctrl-A X` termination. |
| Migration attempts to serialize host pointers | Migrate only emulated PCM/tone state and reconstruct the voice on the destination. |
| Interactive-only testing hides regressions | Make WAV analysis the automated acceptance test and treat CoreAudio as a smoke test. |

## 11. Follow-up: host microphone loopback

After playback is stable, replace or supplement the synthetic capture source
with `SWVoiceIn`:

1. add a 48 kHz stereo signed-16 input voice;
2. buffer host input independently from output;
3. have the WM8904 capture endpoint consume input frames, using silence on
   underrun;
4. retain `tone` and `ramp` modes for deterministic tests;
5. document macOS microphone permissions and feedback risk; and
6. recommend headphones to avoid acoustic feedback during live loopback.

Host capture is intentionally separate because permissions, absent-input
behavior, feedback, and two independently paced rings materially expand the
test surface.
